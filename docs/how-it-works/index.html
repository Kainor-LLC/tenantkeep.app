A run, end to end

  1. Sign in. Locally, the admin signs in to Graph, Exchange, Purview, SharePoint, Teams and Azure (macOS needs separate processes for some; docs/collection.md). In Automation, the account's managed identity signs in to everything except Purview (see Identities).
  2. Collect. Invoke-PostureCollection writes one evidence folder per run: JSON and CSV files named after the audit plan (04-role-assignments-active.csv, exo-04-antiphish.json, ...), a collection.json manifest with the tenant id, account, scopes, API versions and errors, and the Conditional Access snapshot. Every Graph call pins its API version. Nothing leaves the customer's environment.
  3. Profile. New-PostureProfile discovers what evidence can tell (licences, platforms, identity model, BYOD, Copilot) and asks only what it cannot (third-party tools, thresholds, break-glass accounts, frameworks, audience). The result is profile.json in the client folder, beside brand.json, exceptions.json, tenantkeep.lic and findings.csv.
  4. Evaluate. The engine reads the catalog, applies the baseline, asks one fact provider per domain for facts and affected objects from the evidence, evaluates each check's pass expression against thresholds, applies exceptions (accepted risk counts as a pass), third-party coverage and licence applicability. checks.json records every result with its reason, evidence files and affected list.
  5. Report. New-PostureReport builds a model (score, headline numbers, domain scorecards, top risks, admins, Copilot readiness, Conditional Access, recommendations, trend against a previous run, crosswalk, appendix) and renders it. Export-PostureFindings writes the register, merging owner, status, effort and dependency by check id from the previous register.
  6. Keep. Locally the run folder stays under ~/tenantkeep/evidence/. In Automation it is uploaded to the posture-runs container, the register is written back to the client container, old runs are pruned.

Identities and permissions

  • Local runs use the signed-in admin's delegated permissions. Global Reader covers most reads; Exchange needs View-Only Organization Management, SharePoint the SharePoint Administrator role with the Tenantkeep SharePoint app (delegated, created by New-PostureSharePointApp.ps1), Purview a compliance read role, Azure Reader and Security Reader.
  • Automation uses the account's system-assigned managed identity. Grant-ManagedIdentityGraphRole.ps1 -IncludePosture gives it the Graph application roles every collector needs, Exchange.ManageAsApp, SharePoint Sites.FullControl.All (verify the least that works), the Teams tenant admin API role and the Global Reader directory role; the deployer adds Reader and Security Reader on the subscriptions. The identity also has Storage Blob Data Contributor on the deployment's storage account and nothing else.
  • Purview in Automation (decided and built 2026-10-15, first live run pending): Microsoft's module has no managed identity sign-in for Purview, only a certificate-backed app registration. The customer's setup script creates that app and a certificate in a Key Vault in the customer's own subscription; the managed identity reads the certificate at run time and signs in with it. The certificate never appears in code, configuration, the runbook or this repository, and the customer can revoke it at any time. This is the one exception to "delegated or managed identity only", and it is the customer's credential in the customer's vault.
  • No secrets anywhere else. No app secrets in code or config, no callbacks, no telemetry.

Licensing and integrity

  • A licence is a small JSON file: tenant id, tier (ca or full), customer, issued and expiry dates, key id, and an ECDSA P-256 signature over the canonical fields. The module ships the public keys; the private key is in Kainor's Key Vault (kv-tkp-lic-9195) and never leaves it. Verification is offline and binds the licence to the tenant id the evidence recorded. The Conditional Access domain and the three CA cmdlets are free; everything else needs full. docs/licensing.md has the detail and the honest limits.
  • Issuing is automatic: a Stripe payment link with a Tenant ID field, a webhook to an Azure Function in the Kainor tenant, a signature through Key Vault, an email from licensing@kainor.com, a row in the register. Renewals re-issue.
  • Releases carry a signed integrity.json (every file's hash). At import the module checks itself and prints the build state, release, development or modified, in every report header. A label, not a lock.

The report site (Option B opt-in, decided 2026-10-15, being built)

The report is a file, so until now "save an exception" meant editing exceptions.json by hand. The report site makes the browser the place of record: a small web app in the customer's subscription, signed in with the customer's own Entra accounts, that serves the latest report and accepts saves. Exceptions, the register (owner, status, effort, dependency) and the tenant configuration (thresholds, third-party tools, baseline, break-glass accounts, frameworks) are written to the client container, which is exactly what the next scheduled run reads. Recording an exception re-scores the page immediately; the next run makes it permanent. Design details are in docs/report-site.md once built.

What is still manual

  • The Windows AD collector runs on a domain-joined machine and its files are copied into the evidence folder (local) or the client/hybrid/ prefix (Automation). A Hybrid Runbook Worker is the v1.1 answer.
  • Purview in Automation until the customer runs New-PosturePurviewApp.ps1 once.
  • Role grants and app registrations: always the customer's admin, by design.
